# PRD — PS26019

**Problem Statement ID:** PS26019  
**Title:** National Digital Platform for Research, Policy Innovation, and Evidence-Based Land Governance  
**Category:** Software  
**Theme:** Smart Automation  
**Status:** MVP — Offline-First + SQLite + Local AI/RAG with llama.cpp

---

## 1. Product Vision

Build a national-ready **evidence-to-decision platform for land governance** that connects:

**Research & policy evidence → government datasets → GIS → analytics → policy scenario simulation → explainable decision insights**

### Core value proposition

> **From scattered land evidence to an explainable policy what-if decision.**

The MVP must demonstrate one complete decision workflow rather than attempting to implement every possible land-governance capability.

### Product principle

> **Do not build a better map. Build a better decision workflow.**

---

## 2. Problem Being Solved

Land-governance information is distributed across research papers, policy documents, legal material, government datasets, geospatial layers and land-use records.

Users currently need to:

- search multiple sources;
- understand different data formats;
- combine documents with spatial datasets;
- analyze historical land-use change;
- interpret geographic impacts;
- manually evaluate policy alternatives;
- prepare evidence-backed conclusions.

PS26019 brings these activities into one workflow.

---

## 3. MVP Scope

The MVP will implement five connected capabilities:

1. **Evidence Explorer**
2. **GIS Land Intelligence**
3. **Historical/Descriptive Analytics**
4. **Explainable Policy Scenario Simulator**
5. **AI Evidence-Backed Insight**

### MVP demonstration scenario

> **Controlled agricultural-to-built-up land conversion around an expanding urban area.**

### Demonstration geography

**Kolkata / peri-urban West Bengal**, using a bounded study area and prepared datasets.

# 4. Functional Requirements

## 4.1 Evidence Explorer

The system shall provide a searchable local knowledge base containing selected:

- DoLR documents;
- DILRMP material;
- government reports;
- policy papers;
- research material;
- dataset descriptions;
- legal/reference documents where relevant.

### Required functions

- keyword search;
- full-text search;
- semantic/hybrid retrieval;
- document metadata;
- source attribution;
- document/chunk references;
- evidence snippets;
- AI-assisted evidence synthesis.

The MVP knowledge base must be usable without internet access after setup.

---

## 4.2 GIS Land Intelligence

The system shall provide an interactive map for the selected study area.

### Required layers

- administrative boundaries;
- land-use/land-cover (LULC);
- urban/built-up areas;
- agricultural areas;
- settlements;
- roads/infrastructure where available;
- selected governance indicators.

### Required GIS functions

- pan/zoom;
- layer visibility;
- legend;
- feature inspection;
- region/study-area selection;
- baseline map;
- scenario-result map;
- affected-area highlighting.

Large geospatial files shall remain outside SQLite and be referenced through metadata.

---

## 4.3 Historical Analytics

The system shall calculate deterministic, reproducible indicators such as:

- area by land-use class;
- agricultural area;
- built-up area;
- percentage distribution;
- historical land-use change;
- change between selected periods;
- affected spatial units;
- scenario impact statistics.

Numerical results must be generated by application code, not by the LLM.

---

## 4.4 Explainable Policy Scenario Simulator

The simulator shall allow the user to configure a controlled policy scenario.

### Example inputs

- target study area;
- requested conversion area;
- proximity to existing urban areas;
- infrastructure-access preference;
- population-pressure preference;
- environmental constraints;
- scoring weights.

### Processing

1. Load baseline dataset.
2. Identify eligible areas.
3. Apply constraints.
4. Calculate suitability score.
5. Rank eligible areas.
6. Allocate requested area.
7. Recalculate indicators.
8. Generate spatial impact layer.
9. Compare baseline and scenario.
10. Store scenario parameters and results.

### Example scoring model

```text
Score =
    w1 × UrbanProximity
  + w2 × PopulationPressure
  + w3 × InfrastructureAccess
  - w4 × EnvironmentalConstraint
```

The exact weights must be visible to the user.

### Important limitation

The simulator is **scenario analysis and decision support**, not an authoritative prediction of future land use.

# 5. AI/RAG Requirements

## 5.1 Local-First AI

The default AI architecture shall be completely local.

### Required default stack

**llama.cpp** shall be used as the local LLM inference runtime.

The MVP shall not require:

- OpenAI API;
- Gemini API;
- Claude API;
- cloud-hosted inference;
- cloud vector databases.

The system must remain functional when the LLM is unavailable.

---

## 5.2 Plug-and-Play LLM Architecture

The application shall communicate with an abstract provider interface rather than directly depending on a specific model runtime.

```python
class LLMProvider:
    def generate(self, prompt: str, context: dict) -> str:
        raise NotImplementedError

    def health(self) -> bool:
        raise NotImplementedError
```

### Default provider

```text
LLMProvider
     ↓
LocalLLMProvider
     ↓
llama.cpp
     ↓
Local GGUF Model
```

### Optional future providers

```text
LLMProvider
 ├── LocalLLMProvider → llama.cpp
 ├── OpenAIProvider   → OpenAI API
 ├── GeminiProvider   → Gemini API
 └── OtherProvider    → Future integration
```

Cloud providers are optional extensions and are not part of the offline MVP dependency chain.

---

# 6. RAG Architecture

The local RAG pipeline shall be:

```text
Documents
   ↓
Text Extraction
   ↓
Cleaning
   ↓
Chunking
   ↓
Metadata + Source IDs
   ↓
Local Index
   ├── SQLite FTS5
   └── Local Embeddings / Vector Index
   ↓
Hybrid Retrieval
   ↓
Evidence Filtering
   ↓
Prompt Builder
   ↓
llama.cpp
   ↓
Grounded Insight
   ↓
Source References
```

### RAG rules

- retrieved evidence must be passed to the LLM as context;
- source IDs must be retained;
- answers must distinguish evidence from interpretation;
- unsupported claims must not be presented as facts;
- numerical simulation results must come from deterministic code;
- the LLM must not modify stored simulation results;
- prompt-injection content in documents must be treated as untrusted data.

# 8. Database Requirements

## Primary Database: SQLite

SQLite shall be the single primary application database for the MVP.

### Reasons

- serverless;
- portable;
- simple deployment;
- easy backup;
- suitable for a single-machine hackathon MVP;
- no database server required.

### Core tables

```text
users
roles
documents
document_chunks
datasets
dataset_versions
regions
landuse_observations
analytics_results
scenarios
scenario_runs
scenario_results
model_versions
audit_logs
```

### SQLite responsibilities

SQLite stores:

- users and roles;
- document metadata;
- document chunks;
- dataset metadata;
- dataset versions;
- region metadata;
- derived indicators;
- scenario definitions;
- scenario runs;
- scenario results;
- AI/model configuration metadata;
- audit information.

### Geospatial storage strategy

SQLite is not a replacement for PostGIS.

Therefore:

- small geometry payloads may use GeoJSON/WKB;
- large vector layers remain GeoJSON/GeoPackage/files;
- rasters remain files;
- SQLite stores paths, metadata and versions;
- GeoPandas/Shapely perform spatial operations;
- frontend receives simplified GeoJSON for visualization.

Future PostgreSQL/PostGIS migration is possible if national-scale deployment requires it.

# 10. Local AI Technology Stack

## 10.1 LLM Runtime

### Required

**llama.cpp**

Use a local **GGUF-compatible quantized model**.

The exact model shall be selected based on:

- available RAM/VRAM;
- CPU/GPU capability;
- response quality;
- context-window needs;
- license suitability.

The model itself is not hard-coded into the application.

---

## 10.2 Local LLM Integration

The backend shall communicate with llama.cpp through a dedicated adapter.

```text
Backend
   ↓
LLMProvider
   ↓
LlamaCppProvider
   ↓
llama.cpp server/runtime
   ↓
GGUF model
```

The provider should expose:

- health check;
- model information;
- generation;
- configurable temperature;
- configurable max tokens;
- configurable context length;
- timeout/error handling.

---

## 10.3 Embeddings

Embeddings shall also be local-first.

Possible implementation:

- local sentence-transformer-compatible embedding model;
- ONNX/runtime-based local embedding implementation;
- another offline embedding implementation selected during development.

The embedding implementation must be isolated behind an interface so it can be replaced.

---

## 10.4 Retrieval

MVP retrieval should use:

1. SQLite FTS5 keyword retrieval;
2. local semantic retrieval where feasible;
3. metadata/source filtering;
4. hybrid ranking.

A dedicated vector database is **not required** for the MVP.

---

# 11. Cloud AI Option

# 13. Configuration Requirements

Configuration shall be environment-based.

Example:

```env
APP_ENV=local

DATABASE_URL=sqlite:///./database/ps26019.db

LLM_PROVIDER=local
LLM_RUNTIME=llama.cpp

LLAMA_CPP_BASE_URL=http://127.0.0.1:8080
LLAMA_CPP_MODEL=local-model.gguf

EMBEDDING_PROVIDER=local
EMBEDDING_MODEL=local-embedding-model

RAG_ENABLED=true

AUTH_ENABLED=true
```

No API key should be required for the default offline configuration.

## 13.1 Plug-and-Play Configuration

Decisions that may change during dataset preparation or hardware evaluation must
be selected through configuration and versioned profiles, not hard-coded into
business logic.

The MVP shall isolate these replaceable choices behind stable interfaces:

| Decision | Configuration/interface |
|---|---|
| Study boundary | `StudyAreaProvider` and region profile |
| Source datasets | `DatasetProfile` and dataset registry |
| Simulation spatial unit | `SpatialUnitProvider` |
| Scenario weights | versioned scenario configuration |
| Validation method | `ValidationStrategy` |
| Chat model | `LLMProvider` and model configuration |
| Embedding model | `EmbeddingProvider` and model configuration |
| Authentication implementation | `AuthProvider` |

Changing one of these selections must not require changes to the frontend
workflow, simulation orchestration, RAG orchestration or persistence contract.
Each selected profile must record its identifier and version in SQLite and in
the relevant audit or result record.

The fixed MVP contract remains unchanged: SQLite, offline-first execution,
local llama.cpp inference with GGUF, deterministic calculations and the
Kolkata/peri-urban demonstration workflow.

# 14. AI Responsibilities vs Deterministic Responsibilities

## AI is responsible for

- evidence summarization;
- natural-language explanation;
- document question answering;
- evidence synthesis;
- identifying relevant retrieved sources;
- explaining scenario assumptions and limitations.

## AI is NOT responsible for

- authoritative calculations;
- land-area calculations;
- GIS geometry operations;
- scenario allocation;
- database integrity;
- access control;
- modifying simulation results;
- inventing sources;
- claiming unsupported causality.

### Principle

> **Code calculates. AI explains.**

# 18. Non-Functional Requirements

## Performance

The MVP should provide interactive response for:

- normal search;
- map interaction;
- standard analytics;
- small/medium scenario runs.

Long-running tasks may show progress states.

## Reliability

If local AI fails:

```text
Evidence Explorer      → Works
GIS                    → Works
Analytics              → Works
Simulation             → Works
AI Insight             → Unavailable state
```

The application must not crash because the LLM is unavailable.

## Reproducibility

The same:

- dataset version;
- study area;
- scenario parameters;
- scoring weights;
- simulator version

should produce the same deterministic simulation result.

## Portability

The MVP should run on a single local machine without requiring:

- Kubernetes;
- cloud database;
- external API;
- distributed services.

# 24. Architecture Decision Summary

### Mandatory decisions

- **Offline-first**
- **SQLite**
- **Python/FastAPI backend**
- **React/TypeScript frontend**
- **GeoPandas/Shapely for GIS processing**
- **llama.cpp for local LLM inference**
- **Local embeddings**
- **SQLite FTS5**
- **Provider abstraction for LLMs**
- **Deterministic simulation**
- **Evidence provenance**
- **AI as an explainability layer**

### Optional decisions

- cloud LLM providers;
- SpatiaLite;
- sqlite-vec;
- PostgreSQL/PostGIS in future;
- dedicated vector database in future;
- cloud deployment in future.

### Core engineering principle

> **The platform should be fully usable locally first, while its AI layer remains replaceable so cloud models can be added later without redesigning the application.**
